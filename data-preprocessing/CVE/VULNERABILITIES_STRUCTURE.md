# `vulnerabilities.json` Field Reference

Full attribute-by-attribute breakdown of every record in `vulnerabilities.json`
(346,947 records after preprocessing). Percentages are "present on this % of
the 346,947 records" unless a row is explicitly scoped to a nested array
(in which case the percentage is relative to that array's own entry count).
Generated by walking every record in the file, not sampled.

Every record is one STIX 2.1 `vulnerability` object for one CVE.

## Top-level fields

| Field | Type | Present | Description |
|---|---|---|---|
| `id` | string | 100% | STIX object id, `vulnerability--<uuid5>`. Deterministic — a UUIDv5 hash of the CVE id (`cve:<CVE-ID>`), not random, so the same CVE always gets the same id across re-crawls. |
| `type` | string | 100% | STIX object type discriminator. Constant: always `"vulnerability"`. |
| `spec_version` | string | 100% | STIX spec version this object conforms to. Constant: always `"2.1"`. |
| `name` | string | 100% | The CVE identifier itself, e.g. `"CVE-1999-0001"`. Format `CVE-\d{4}-\d+`, verified against all 346,947 records with zero mismatches. |
| `description` | string | 100% | English-language vulnerability description from NVD. Never empty (min length 15 chars, max 3,998). |
| `created` | string | 100% | ISO-8601 timestamp (STIX format, e.g. `"1999-12-30T05:00:00.000Z"`) — NVD's `published` date, i.e. when the CVE record first appeared in NVD. |
| `modified` | string | 100% | ISO-8601 timestamp — NVD's `lastModified` date, i.e. the last time NVD updated any part of this record (description, CVSS scores, CWE mapping, etc.). |
| `x_nvd_vuln_status` | string (enum) | 100% | NVD's workflow status for this CVE. See [Status values](#x_nvd_vuln_status-values) below. (`"Rejected"` records are filtered out entirely during preprocessing — see the CVE README — so that value never appears here.) |
| `x_nvd_source_identifier` | string | 100% | Identifier of the organization that owns/submitted this CVE record — either an email address (e.g. `"cve@mitre.org"`, `"psirt@adobe.com"`) or a UUID standing in for an org without a public email. 455 distinct values across the dataset; free-form, not a fixed enum. |
| `x_nvd_cvss` | object | 100% | Container for every CVSS/SSVC scoring metric NVD has recorded for this CVE, keyed by metric-version name. See [`x_nvd_cvss`](#x_nvd_cvss) below — this is where almost all the structural complexity lives. |

### `x_nvd_vuln_status` values

| Value | Count | Meaning |
|---|---|---|
| `Modified` | 240,939 (69.4%) | Analyzed at least once, then updated again afterward (new references, revised CVSS, etc.). NVD's most common terminal state. |
| `Analyzed` | 64,657 (18.6%) | NVD has completed its analysis (CVSS scoring, CWE mapping, CPE applicability) and not touched it since. |
| `Deferred` | 39,255 (11.3%) | NVD has decided not to (or not yet) perform its own analysis — typically because a CNA already supplied CVSS/CWE data NVD considers sufficient. |
| `Awaiting Analysis` | 1,507 (0.4%) | Published but still queued for NVD's analysis team. |
| `Received` | 335 (0.1%) | Just ingested from a CNA; the earliest pre-analysis state. |
| `Undergoing Analysis` | 254 (0.1%) | NVD analysis is actively in progress. |

## `x_nvd_cvss`

Raw copy of NVD's own `metrics` object (`cve.metrics` in the NVD API response),
kept embedded as an attribute rather than extracted into relationships — see
the CVE README for why. It is an object whose keys are metric-version names;
**a CVE can have any subset of these five keys, including none** (1,553
records / 0.4% have `x_nvd_cvss: {}` — typically very recently published CVEs
NVD hasn't scored yet). 20 distinct combinations of keys occur in practice;
the three most common are `{cvssMetricV31, ssvcV203}` (114,725 records),
`{cvssMetricV2}` alone (72,390), and `{cvssMetricV2, cvssMetricV31}` (52,010).

| Key | Present | What it is |
|---|---|---|
| `cvssMetricV2` | 194,422 (56.0%) | CVSS version 2.0 scores (the original, now-legacy standard) |
| `cvssMetricV30` | 54,532 (15.7%) | CVSS version 3.0 scores |
| `cvssMetricV31` | 225,833 (65.1%) | CVSS version 3.1 scores (the most common version in the dataset) |
| `cvssMetricV40` | 29,422 (8.5%) | CVSS version 4.0 scores (the newest standard, only used on recent CVEs) |
| `ssvcV203` | 163,212 (47.0%) | CISA's Stakeholder-Specific Vulnerability Categorization, version 2.0.3 — a decision-tree model, not a numeric score |

Each key's value is a **list**, not a single object — because a CVE can carry
more than one assessment of the same metric version at once, e.g. NVD's own
"Primary" score alongside a CNA's "Secondary" score. Array length is 1 for
the large majority of records but goes up to 4 in rare cases:

| Field | Length 1 | Length 2 | Length 3 | Length 4 |
|---|---|---|---|---|
| `cvssMetricV2` | 194,299 | 123 | – | – |
| `cvssMetricV30` | 52,725 | 1,807 | – | – |
| `cvssMetricV31` | 149,351 | 76,082 | 399 | 1 |
| `cvssMetricV40` | 29,418 | 4 | – | – |
| `ssvcV203` | 163,067 | 143 | – | 2 |

### `cvssMetricV2[]` entries

| Attribute | Type | Present (of V2 entries) | Description |
|---|---|---|---|
| `source` | string | 100% | Org id that produced this score. 8 distinct values — dominated by `nvd@nist.gov` (180,076) and `cna@vuldb.com` (14,299), plus a handful of others in the low tens. |
| `type` | string (enum) | 100% | `Primary` (180,076) — NVD's own authoritative score — or `Secondary` (14,469) — a CNA-supplied score NVD is also recording alongside its own. |
| `baseSeverity` | string (enum) | 100% | `MEDIUM` (112,557), `HIGH` (61,490), `LOW` (20,498). Note: unlike v3/v4, CVSS v2 has no official severity-band standard — this is NVD's own qualitative bucketing of the `baseScore`, and it sits at this level (a sibling of `cvssData`), not inside `cvssData` itself. |
| `exploitabilityScore` | float | 100% | The "exploitability" sub-score component of the CVSS v2 formula (0–10) — how easy the vulnerability is to reach and trigger. |
| `impactScore` | float | 100% | The "impact" sub-score component (0–10) — how severe the consequences are once exploited. |
| `acInsufInfo` | bool | 100% | "Access Complexity — insufficient information": flags that the scorer felt there wasn't enough information to confidently rate Access Complexity. |
| `obtainAllPrivilege` | bool | 100% | Whether successful exploitation grants the attacker all privileges on the target. |
| `obtainOtherPrivilege` | bool | 100% | Whether it grants privileges belonging to a different user/context than the attacker's own. |
| `obtainUserPrivilege` | bool | 100% | Whether it grants regular user-level privileges. |
| `userInteractionRequired` | bool | 99.5% | Whether a victim must take some action (e.g. open a file) for exploitation to succeed. The only optional field in this shape — missing on ~973 entries. |
| `cvssData` | object | 100% | The actual CVSS v2 vector — see below. |

| `accessComplexity` | string (enum) | `LOW` (118,925), `MEDIUM` (69,791), `HIGH` (5,829) — how hard the attack is to pull off |

| `confidentialityImpact` | string (enum) | `PARTIAL` (98,029), `NONE` (62,964), `COMPLETE` (33,552) |

| `availabilityImpact` | string (enum) | `PARTIAL` (86,374), `NONE` (69,264), `COMPLETE` (38,907) |
| `baseScore` | float | 0.0–10.0 |

### `cvssMetricV30[]` / `cvssMetricV31[]` entries

Identical shape between the two versions — only the `cvssData.version` value
and the underlying score distributions differ. (v3.0's `type` split is
41,463 `Primary` / 14,876 `Secondary`; v3.1 is more evenly split, 149,799
`Primary` / 152,917 `Secondary`, which is why v3.1 entries reach array length
2–4 far more often than v3.0.)

| Attribute | Type | Description |
|---|---|---|
| `source` | string | Same convention as v2 — id of the org that produced this score |
| `type` | string (enum) | `Primary` / `Secondary`, same meaning as v2 |
| `exploitabilityScore` | float | Exploitability sub-score (0–10) |
| `impactScore` | float | Impact sub-score (0–10) |
| `cvssData` | object | The CVSS v3.x vector — see below |

### `cvssMetricV40[]` entries

CVSS v4.0 is the newest standard and reshapes several v3 concepts; NVD only
just started scoring with it, so coverage is much lower (8.5%) and skewed
toward `Secondary` (29,421 `Secondary` vs only 5 `Primary` — almost all v4.0
scores in this dataset came from CNAs, not NVD itself).

| Attribute | Type | Description |
|---|---|---|
| `source` | string | Org id, dominated by CNAs (`cna@vuldb.com`, `disclosure@vulncheck.com`, `security-advisories@github.com`, …) rather than NVD itself |
| `type` | string (enum) | `Primary` (5) / `Secondary` (29,421) |
| `cvssData` | object | The CVSS v4.0 vector — see below. Note: v4.0 has no `exploitabilityScore`/`impactScore` sibling fields the way v2/v3 do — those sub-scores aren't part of the v4.0 model. |

### `ssvcV203[]` entries

CISA's **Stakeholder-Specific Vulnerability Categorization**, version 2.0.3 —
a decision-tree triage model (not a numeric score) that outputs a small set
of categorical decision points instead of a 0–10 score.

| Attribute | Type | Description |
|---|---|---|
| `source` | string | Org id of the assessor. 8 distinct values, overwhelmingly one CISA uuid (`134c704f-...`, 163,215 of 163,361 entries). |
| `ssvcData` | object | The assessment payload — see below. |

`ssvcData`:

| Attribute | Type | Present (of SSVC entries) | Description |
|---|---|---|---|
| `id` | string | 100.0% (163,338/163,361) | The CVE id again — a redundant echo of the parent record's own `name`. |
| `role` | string (enum) | 100% | `CISA Coordinator` (163,337), `CNA` (23), `Coordinator` (1) — the capacity in which the assessor is scoring this CVE. |
| `version` | string | 100% | Constant `"2.0.3"`. |
| `timestamp` | string | 100.0% (163,337/163,361) | ISO-8601 timestamp of when this SSVC assessment was made. |
| `options` | array | 100% | **Not** a single object with three keys — a list of separate single-key objects, one per decision point. See below. |

`ssvcData.options[]` — each element is a single-key object; a complete
`ssvcData` normally carries exactly three of these, one per key:

```json
"options": [
  { "exploitation": "none" },
  { "automatable": "yes" },
  { "technicalImpact": "total" }
]
```

| Key (appears alone in its own object) | Type (enum) | Values (count) | Meaning |
|---|---|---|---|
| `exploitation` | string | `none` (123,367), `poc` (38,352), `active` (1,642) | Evidence of exploitation seen in the wild: none, proof-of-concept only, or active exploitation |
| `automatable` | string | `no` (126,130), `yes` (37,231) | Whether the exploit steps can be automated (scan → exploit → propagate) at scale |
| `technicalImpact` | string | `partial` (108,195), `total` (55,166) | Degree of control/damage gained on successful exploitation |

## Fields removed during preprocessing (not present in `vulnerabilities.json`)

For reference — see the CVE preprocessing README for the full rationale:

- `external_references` — dropped entirely (redundant self-reference plus non-entity bibliography URLs).
- `x_nvd_configurations` (CPE applicability data) — dropped entirely (nested AND/OR boolean tree, no lossless flat edge to extract).
- `x_nvd_weaknesses` — removed from the entity record and rebuilt as `CVE --related-to--> CWE` edges in `external_relationships.json` (real `CWE-N` ids only; NVD-only labels like `NVD-CWE-noinfo`/`NVD-CWE-Other` are dropped).
- Records with `x_nvd_vuln_status == "Rejected"` — dropped outright (empty shells).
